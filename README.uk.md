# workspace-status-mcp

*[English](README.md)*

MCP-сервер з трьома інструментами:

- `sweep_status` — знімок стану всіх git-репозиторіїв у заданій теці
  одним викликом: гілка, незакомічені зміни, неопубліковані коміти й
  (опційно) статус останнього GitHub Actions CI-запуску. Заміняє ручний
  цикл `git status` + `gh run list` по кожному з десятків репо окремо.
- `check_docs` — позначає, документація якого репо (`Architecture/<repo>.
  txt`) відсутня чи старша за останній коміт репо. Сам нічого не пише й
  не генерує (розуміння коду достатньо, щоб його задокументувати, - це
  завдання для AI/людини, не для скрипта) - лише каже, куди дивитись, щоб
  документація оновлювалась свідомо, а не тихо застарівала.
- `check_release_drift` — для явних пар (репо з вихідним кодом, репо, що
  тегує релізи) рахує, скільки комітів з'явилось у джерелі відколи реліз
  востаннє тегувався, і наскільки давно найстарший із них. Вирізати
  реліз - зазвичай ручний крок "коли згадаю" (тег версії, пуш, CI
  збирає й публікує) - цей інструмент відповідає "чи хтось це реально
  робив останнім часом" без ручної перевірки.

## Навіщо

Працюючи одночасно з ~50 репозиторіями в одному робочому просторі,
питання "що з усього цього реально потребує уваги прямо зараз" виникало
знову й знову в межах однієї сесії — і щоразу перевірялось вручну, репо
за репо. `sweep_status` відповідає на нього одним викликом і за
замовчуванням повертає ЛИШЕ ті репо, що справді потребують погляду
(брудне робоче дерево, неопубліковані коміти, або CI, що не в статусі
чистого success) — чисті репо мовчки пропускаються, щоб відповідь
лишалась короткою.

`check_docs` існує з тієї самої причини, на рівень вище: архітектурна
документація проєкту корисна, лише якщо їй довіряють, а довіряють їй,
лише якщо хтось справді перевіряє її актуальність. Порівняння "останній
коміт" з "час зміни документа" перетворює це з речі, яку треба пам'ятати,
на річ, яку можна просто спитати.

## Встановлення

```bash
npm install
```

Для статусу CI (`check_ci: true`, за замовчуванням) потрібен
автентифікований GitHub CLI (`gh`). Без нього результат CI просто
повертається як `null` для кожного репо.

## Інструмент: `sweep_status`

| Аргумент | Тип | За замовчуванням | Значення |
|---|---|---|---|
| `root` | string | — (обов'язково) | Тека для сканування, один рівень углиб (напр. `/home/user/Projects`) |
| `repos` | string[] | усі підтеки | Обмежитись конкретними назвами репо замість повного сканування |
| `check_ci` | boolean | `true` | Також опитувати GitHub Actions на останній запуск кожного репо |
| `only_attention` | boolean | `true` | Повертати лише репо, що потребують уваги; `false` — усе |

Кожен запис репо: `name`, `path`, `branch`, `uncommittedFiles` (кількість),
`ahead`/`behind` (відносно upstream, `null` якщо upstream не налаштовано),
`hasUpstream`, і `ci` (`{status, conclusion, workflow, url}` або `null`).

## Інструмент: `check_docs`

| Аргумент | Тип | За замовчуванням | Значення |
|---|---|---|---|
| `projectsRoot` | string | — (обов'язково) | Тека з репозиторіями |
| `docsRoot` | string | `<projectsRoot>/Architecture` | Тека з `<repo>.txt`-документацією |
| `repos` | string[] | усі підтеки | Обмежитись конкретними назвами репо |
| `only_attention` | boolean | `true` | Лише missing/stale; `false` — усе, включно з `current` |

Кожен запис репо: `name`, `docPath`, `status` (`missing` / `stale` /
`current` / `no-commits`), `lastCommitAt`, `docUpdatedAt`, і
`staleBySeconds` (лише при `stale`).

## Інструмент: `check_release_drift`

| Аргумент | Тип | За замовчуванням | Значення |
|---|---|---|---|
| `projectsRoot` | string | — (обов'язково) | Тека з репозиторіями |
| `pairs` | `{source, release}[]` | — (обов'язково) | Явний список пар назв тек джерело→реліз |
| `only_attention` | boolean | `true` | Лише `drifted`; `false` — усе, включно з `current`/`no-tags` |

Кожен запис пари: `source`, `release`, `status` (`drifted` / `current` /
`no-tags`), і при `drifted`: `latestTag`, `tagCreatedAt`,
`commitsSinceTag`, `oldestUnreleasedCommitAt`, `oldestUnreleasedAgeDays`.

## Архітектура

- `src/sweep.js` — уся логіка: знаходить теки з `.git` на один рівень
  углиб від `root` (експортовано як `findGitRepos`, перевикористовує
  `docs.js`), тоді для кожної паралельно (пакетами по 8, щоб не бомбити
  GitHub API) запускає `git branch`/`git status`/`git rev-list` і
  (опційно) `gh run list`.
- `src/docs.js` — `checkDocs()`: для кожного репо `git log -1 --format=
  %ct` проти часу зміни файлу документації, порівняно як Unix-timestamps
  (без мороки з часовими поясами). Репо ще без жодного коміту звітує
  `no-commits`, а не мовчки потрапляє в `missing` чи `current`.
- `src/server.js` — реєструє обидва інструменти через MCP SDK на
  stdio-транспорті.
- `test/smoke.mjs` — `sweep_status` проти реальних локальних репо (без
  штучних фікстур — у самому робочому просторі вже є й чисті, і брудні
  репо, і репо без upstream).
- `test/docs.mjs` — `check_docs` проти тимчасових одноразових
  git-репозиторіїв з контрольованими таймстемпами комітів/файлів
  (реальна `~/Projects` дрейфує з часом, тест на ній був би нестабільним).
- `src/release-drift.js` — `checkReleaseDrift()`: знаходить останній тег
  реліз-репо через `git for-each-ref --sort=-creatordate` (сортування за
  реальним часом тега, не семвер-рядком `-v:refname` - інакше `v1.10`
  сортувався б ПЕРЕД `v1.9`), тоді рахує `git log --since=@<tagTimestamp>`
  у репо-джерелі. Зв'язок джерело↔реліз не вгадується зі структури тек
  (немає загального правила "тека X випускає теку Y") - викликач передає
  пари явно.
- `test/release-drift.mjs` — тимчасові репо з явними
  `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` на кожен коміт (не покладаючись
  на реальні розриви в часі між комітами, зробленими за мілісекунди один
  від одного в межах тесту, - секундна точність `git log --since` інакше
  могла б зробити тест нестабільним), плюс один живий тест на реальній
  парі NyxilumLang→NyxilumNode, що лише перевіряє відсутність падіння.
