# workspace-status-mcp

*[English](README.md)*

MCP-сервер з чотирма інструментами:

- `sweep_status` — знімок стану всіх git-репозиторіїв у заданій теці
  одним викликом: гілка, незакомічені зміни, неопубліковані коміти й
  (опційно) статус останнього GitHub Actions CI-запуску. Заміняє ручний
  цикл `git status` + `gh run list` по кожному з десятків репо окремо.
- `check_docs` — позначає, документація якого репо (`Architecture/<repo>.
  txt`) відсутня чи застаріла. Сам нічого не пише й не генерує (розуміння
  коду достатньо, щоб його задокументувати, - це завдання для AI/людини,
  не для скрипта) - лише каже, куди дивитись, щоб документація
  оновлювалась свідомо, а не тихо застарівала.
- `write_doc` — записує `Architecture/<repo>.txt` і фіксує поточний
  commit-хеш репо, щоб `check_docs` міг згодом виміряти застарілість
  точно (кількість комітів з моменту запису), а не вгадувати за mtime
  файлу.
- `check_release_drift` — для явних пар (репо з вихідним кодом, репо, що
  тегує релізи) рахує, скільки комітів з'явилось у джерелі відколи реліз
  востаннє тегувався, і наскільки давно найстарший із них. Вирізати
  реліз - зазвичай ручний крок "коли згадаю" (тег версії, пуш, CI
  збирає й публікує) - цей інструмент відповідає "чи хтось це реально
  робив останнім часом" без ручної перевірки.

## Навіщо

Працюючи одночасно з ~50 репозиторіями в одному робочому просторі,
питання "що з усього цього реально потребує уваги прямо зараз" виникало
знову й знову в межах однієї сесії — і щоразу перевірялось вручну, репо
за репо. `sweep_status` відповідає на нього одним викликом і за
замовчуванням повертає ЛИШЕ ті репо, що справді потребують погляду
(брудне робоче дерево, неопубліковані коміти, або CI, що не в статусі
чистого success) — чисті репо мовчки пропускаються, щоб відповідь
лишалась короткою.

`check_docs` існує з тієї самої причини, на рівень вище: архітектурна
документація проєкту корисна, лише якщо їй довіряють, а довіряють їй,
лише якщо хтось справді перевіряє її актуальність. Порівняння "останній
коміт" з "час зміни документа" перетворює це з речі, яку треба пам'ятати,
на річ, яку можна просто спитати.

## Хук Claude Code: `check-docs-reminder`

Інструменти вище допомагають, лише якщо їх реально хтось викликає.
`hooks/check-docs-reminder.mjs` закриває саме цю прогалину: зареєстрований
як хук `SessionStart` + `Stop` у `~/.claude/settings.json`, він сам
запускає `checkDocs()` для того репо, в якому зараз працює Claude (піднімається
вгору по теках, шукаючи найближчий git-корінь, що є прямою підтекою
теки з проєктами) - і лише якщо документ того репо відсутній чи застарів,
вставляє одну строчку нагадування прямо в контекст Claude через
`hookSpecificOutput.additionalContext`. В інших випадках - тиша (чисті
репо, робота поза текою з проєктами, або якщо теки `Architecture/` там
взагалі ще не існувало - хто ще не почав користуватись цією конвенцією,
не отримує нагадувань про "відсутню" документацію КОЖНОГО репо). `SessionStart`
покриває "забув із минулої сесії"; `Stop` (спрацьовує щоразу, коли хід
Claude завершується) перевіряє знову кожен хід у межах тієї самої сесії -
і сам замовкає, щойно реально викликано `write_doc`. Навмисно
неблокуючий - застарілий документ вартий нагадування, а не зупинки ходу.

Не прив'язаний до чиєїсь конкретної структури тек, і працює однаково на
Windows і на Linux/macOS. Реєструй через масив `args` ("exec form" -
запускається напряму, без жодного shell, тож немає різниці між
bash/PowerShell/cmd-синтаксисом, про яку треба думати):

```json
{
  "hooks": {
    "SessionStart": [{ "hooks": [{ "type": "command", "command": "node",
      "args": ["/шлях/до/workspace-status-mcp/hooks/check-docs-reminder.mjs", "SessionStart"] }] }],
    "Stop": [{ "hooks": [{ "type": "command", "command": "node",
      "args": ["/шлях/до/workspace-status-mcp/hooks/check-docs-reminder.mjs", "Stop"] }] }]
  }
}
```

### Точки стеження

Не всі репо обов'язково лежать під ОДНИМ коренем - репо могло переїхати з
`~/Projects`, наприклад, на робочий стіл, і документ тоді логічно лежить
прямо поруч із ним там, а не в центральній теці `Architecture/`. Хук
вирішує "точки стеження" (пари `projectsRoot` + опційний `docsRoot`) у
такому порядку, використовуючи ПЕРШУ точку, чий `projectsRoot` містить
поточний репо:

1. CLI-аргументи (`args[2]`/`args[3]` після назви події) - разовий
   перевизначення однієї точки.
2. **Конфіг-файл точок стеження** - типово
   `~/.claude/workspace-status-points.json` (шлях можна змінити через
   `WATCH_POINTS_FILE`). Це звичайний спосіб керувати цим день у день:
   ```json
   {
     "points": [
       { "projectsRoot": "/home/sviat/Projects" },
       { "projectsRoot": "/home/sviat/Десктоп", "docsRoot": "/home/sviat/Десктоп" }
     ]
   }
   ```
   Додати точку, прибрати одну (чи всі), чи перенаправити наявну - просто
   зміною цього файлу, без зміни коду й без перереєстрації хука.
   Відсутній файл, чи порожній/відсутній масив `points` - відкат на
   наступне джерело нижче.
3. Змінні оточення `PROJECTS_ROOT`/`DOCS_ROOT` - запасний варіант для
   однієї точки, якщо хтось реєструє хук через shell-команду замість
   "exec form" з `args`.
4. За замовчуванням: одна точка `<домашня_тека>/Projects`.

`check_docs`/`sweep_status` приймають ту саму ідею напряму як аргументи
`points`/`roots` (див. нижче), якщо хочеш запитати кілька місць прямо з
розмови, без редагування конфіг-файлу.

## Встановлення

```bash
npm install
```

Для статусу CI (`check_ci: true`, за замовчуванням) потрібен
автентифікований GitHub CLI (`gh`). Без нього результат CI просто
повертається як `null` для кожного репо.

Кросплатформно — усі чотири інструменти й хук написані на чистому Node.js
(`path.join`, `os.homedir()`, жодного хардкоду `/`), а зовнішні
команди - `git`/`gh` - працюють нативно і на Windows. Жодного
платформо-специфічного коду.

### Оновлення

Окремого кроку збірки чи публікації нема - `claude mcp add` вказує напряму
на `src/server.js` у цьому клоні, тож оновлення - просто:

```bash
git pull && npm install
```

Набирає чинності з наступної НОВОЇ сесії Claude Code (кожна сесія піднімає
власний процес MCP-сервера, тож вже запущена сесія продовжує працювати з
тим кодом, з яким стартувала).

## Інструмент: `sweep_status`

| Аргумент | Тип | За замовчуванням | Значення |
|---|---|---|---|
| `root` | string | — (обов'язково, якщо нема `roots`) | Тека для сканування, один рівень углиб (напр. `/home/user/Projects`) |
| `roots` | string[] | — | Кілька коренів за один виклик замість одного `root` - результати об'єднуються (напр. репо розкидані між `~/Projects` і деінде) |
| `repos` | string[] | усі підтеки | Обмежитись конкретними назвами репо замість повного сканування (шукає серед усіх коренів) |
| `check_ci` | boolean | `true` | Також опитувати GitHub Actions на останній запуск кожного репо |
| `only_attention` | boolean | `true` | Повертати лише репо, що потребують уваги; `false` — усе |

Кожен запис репо: `name`, `path`, `branch`, `uncommittedFiles` (кількість),
`ahead`/`behind` (відносно upstream, `null` якщо upstream не налаштовано),
`hasUpstream`, і `ci` (`{status, conclusion, workflow, url}` або `null`).

## Інструмент: `check_docs`

| Аргумент | Тип | За замовчуванням | Значення |
|---|---|---|---|
| `projectsRoot` | string | — (обов'язково, якщо нема `points`) | Тека з репозиторіями |
| `docsRoot` | string | `<projectsRoot>/Architecture` | Тека з `<repo>.txt`-документацією |
| `points` | `{projectsRoot, docsRoot?}[]` | — | Кілька незалежних пар корінь+документація за один виклик замість одної `projectsRoot`/`docsRoot` (напр. репо, винесене з `~/Projects`, з документом прямо поруч на новому місці) |
| `repos` | string[] | усі підтеки | Обмежитись конкретними назвами репо (застосовується в межах кожної точки окремо) |
| `only_attention` | boolean | `true` | Лише missing/stale; `false` — усе, включно з `current` |

Кожен запис репо: `name`, `projectsRoot` (з якої точки), `docPath`, `status` (`missing` / `stale` /
`current` / `no-commits`), `trackingMethod` (`commit`, якщо документ
записано через `write_doc`, інакше `mtime` - див. нижче), `lastCommitAt`,
і або `commitsSinceWrite`/`writtenAtCommit`/`writtenAt` (commit-трекінг),
або `docUpdatedAt`/`staleBySeconds` (mtime-трекінг, лише при `stale`).

## Інструмент: `write_doc`

| Аргумент | Тип | За замовчуванням | Значення |
|---|---|---|---|
| `projectsRoot` | string | — (обов'язково) | Тека з репозиторіями |
| `repo` | string | — (обов'язково) | Назва теки репо (напр. `"anylint"`) |
| `content` | string | — (обов'язково) | Повний текст для запису в `<repo>.txt` |
| `docsRoot` | string | `<projectsRoot>/Architecture` | Тека з `<repo>.txt`-документацією |

Записує `<repo>.txt`, а поруч - `.meta/<repo>.json` із commit-хешем HEAD
репозиторія на момент запису. Далі `check_docs` рахує ТОЧНУ кількість
комітів з моменту запису (`git rev-list --count`) замість грубішого
порівняння mtime-документа з часом останнього коміту - той самий патерн,
що вже виправдав себе в `check_release_drift`. Документи, записані напряму
(не через цей інструмент), і далі відстежуються за mtime - порівнювати
просто нема з чим.

## Інструмент: `check_release_drift`

| Аргумент | Тип | За замовчуванням | Значення |
|---|---|---|---|
| `projectsRoot` | string | — (обов'язково) | Тека з репозиторіями |
| `pairs` | `{source, release}[]` | — (обов'язково) | Явний список пар назв тек джерело→реліз |
| `only_attention` | boolean | `true` | Лише `drifted`; `false` — усе, включно з `current`/`no-tags` |

Кожен запис пари: `source`, `release`, `status` (`drifted` / `current` /
`no-tags`), і при `drifted`: `latestTag`, `tagCreatedAt`,
`commitsSinceTag`, `oldestUnreleasedCommitAt`, `oldestUnreleasedAgeDays`.

## Архітектура

- `src/sweep.js` — уся логіка: знаходить теки з `.git` на один рівень
  углиб від кореня (експортовано як `findGitRepos`, перевикористовує
  `docs.js`), тоді для кожної паралельно (пакетами по 8, щоб не бомбити
  GitHub API) запускає `git branch`/`git status`/`git rev-list` і
  (опційно) `gh run list`. `roots` (множина) у `sweepStatus()` запускає
  `findGitRepos` по кожному кореню й об'єднує результати перед
  фільтрацією за `repos`/`only_attention` - тож фільтр за назвою репо
  спрацьовує незалежно від того, під яким саме коренем те репо лежить.
- `src/docs.js` — `checkDocs()`: спершу пробує commit-трекінг
  (`.meta/<repo>.json`, записаний через `write_doc`); якщо його нема -
  відкат на порівняння `git log -1 --format=%ct` з mtime файлу
  документації. Репо ще без жодного коміту звітує `no-commits`, а не
  мовчки потрапляє в `missing` чи `current`. `points` (множина) перевіряє
  кожну незалежну пару projectsRoot+docsRoot по черзі й позначає кожен
  результат, з якої точки він прийшов.
- `src/write-doc.js` — `writeDoc()`: пише `<repo>.txt` і поруч
  `.meta/<repo>.json` (`{commitHash, writtenAt}`, HEAD на момент запису).
  Сам текст не генерує - розуміння коду для документування лишається
  завданням LLM/людини.
- `src/server.js` — реєструє всі чотири інструменти через MCP SDK на
  stdio-транспорті.
- `test/smoke.mjs` — `sweep_status` проти реальних локальних репо (без
  штучних фікстур — у самому робочому просторі вже є й чисті, і брудні
  репо, і репо без upstream), плюс кейс `roots` (множина) проти реального
  кореня й одноразового порожнього.
- `test/docs.mjs` — `check_docs` проти тимчасових одноразових
  git-репозиторіїв з контрольованими таймстемпами комітів/файлів
  (реальна `~/Projects` дрейфує з часом, тест на ній був би нестабільним),
  включно з обома способами трекінгу й кейсом `points` (множина).
- `test/write-doc.mjs` — `writeDoc()` проти тимчасового git-репо:
  правильний HEAD, `.meta/` створюється за потреби, порожній content
  відхиляється.
- `test/hook.mjs` — `hooks/check-docs-reminder.mjs` як реальний
  підпроцес (це CLI-точка входу, не бібліотечна функція): тиша поза
  будь-якою точкою стеження, тиша без жодної теки `Architecture/`,
  нагадування й коректний вибір репо з піддиректорії, конфіг-файл
  точок стеження з двома незалежними точками одночасно, і відкат далі
  по ланцюжку джерел при порожньому/відсутньому `points` у файлі.
- `src/release-drift.js` — `checkReleaseDrift()`: знаходить останній тег
  реліз-репо через `git for-each-ref --sort=-creatordate` (сортування за
  реальним часом тега, не семвер-рядком `-v:refname` - інакше `v1.10`
  сортувався б ПЕРЕД `v1.9`), тоді рахує `git log --since=@<tagTimestamp>`
  у репо-джерелі. Зв'язок джерело↔реліз не вгадується зі структури тек
  (немає загального правила "тека X випускає теку Y") - викликач передає
  пари явно.
- `test/release-drift.mjs` — тимчасові репо з явними
  `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` на кожен коміт (не покладаючись
  на реальні розриви в часі між комітами, зробленими за мілісекунди один
  від одного в межах тесту, - секундна точність `git log --since` інакше
  могла б зробити тест нестабільним), плюс один живий тест на реальній
  парі NyxilumLang→NyxilumNode, що лише перевіряє відсутність падіння.
